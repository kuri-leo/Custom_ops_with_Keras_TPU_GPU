# 基于底层算子行为观察 GPU 与 TPU 的微架构差异

## 引言
在现代机器学习算力基础设施的演进中，底层计算硬件架构的选择直接决定了模型训练与推理的性能上限。GPU 与 TPU 在体系结构设计上反映了两种不同的工程逻辑：通用性（Generality）与特定领域专用性（Domain-Specific Specialization）。本文旨在客观剖析两者的微架构差异，并借助 Google 机器学习工具栈（Keras、JAX、Pallas），以蝶式矩阵（Butterfly Matrix）算法为探针，通过微观实验数据量化验证这些硬件特性的实际表现。

## 1. 核心计算机制与存储体系的物理分歧 (GPU vs TPU)

解决深度学习中海量计算需求的核心挑战，在于如何高效调度数据与算术逻辑单元（ALU）。两者在指令执行模型与数据传导路径上存在根本差异。

### 1.1 计算机制：SIMT 通用并发 vs 脉动阵列空间数据流
GPU 的流式多处理器（SM）架构遵循动态的单指令多线程（SIMT）模型。调度器将线程分组为线程束（Warp），在同一时钟周期内并行执行相同指令但处理不同数据。为支撑这种调度，GPU 硅片上分配了大量面积用于构建控制逻辑（如庞大的寄存器堆、指令解码器、上下文切换单元）。在执行浮点乘加（FMA）时，ALU 需反复读写寄存器。这种冯·诺依曼架构读写模式赋予了 GPU 处理条件分支和不规则内存访问的极高宽容度。

TPU 的矩阵乘法单元（MXU）则采用脉动阵列（Systolic Array）结构。它移除了庞大的动态指令解码和寄存器堆，直接将上万个处理元件（PE）进行物理硬连线。在权重驻留（Weight-Stationary）模式下，参数预加载至 PE，输入特征从阵列一侧按时钟周期规则流入，乘加结果在物理相邻的 PE 间直接传递。这种空间数据流（Spatial Dataflow）彻底消除了中间结果写回寄存器的开销，实现了稠密矩阵乘法（GEMM）在单位周期内的极致吞吐量，但代价是丧失了对非连续寻址和动态控制流的原生处理能力。

### 1.2 存储管理：硬件缓存层级 vs 静态软件调度
GPU 依赖硬件主导的多级缓存（HBM -> L2 -> L1/Shared Memory）。当线程发起读取时，硬件内存控制器尝试在缓存中寻址。开发者可通过 CUDA 或 Triton 显式控制 Shared Memory（通常单 SM 内为 64KB-128KB 级别），但这套系统在面对访存极度离散的网络时，仍易面临缓存抖动和命中率下降。

TPU 采用扁平化的软件托管内存。其核心组件是容量达数 MB 级别的向量内存（VMEM/CMEM），没有硬件缓存一致性协议。数据从 HBM 到 VMEM 的搬运完全交由顶层编译器（如 XLA）在编译期生成直接内存访问（DMA）指令进行静态调度。这种机制允许精确的双缓冲（Double Buffering）流水线设计，消除了访存延迟的不确定性，但要求算法的内存访问模式必须在编译期高度可预测。

## 2. 算子生态与编译框架的层级抽象

硬件的物理特性需要通过编译器与软件栈进行映射。在算子支持层面，两套生态同样呈现出显著差异：

-   CUDA 生态（面向 GPU）：提供细粒度的硬件控制权。开发者可动态分配寄存器、手动同步线程。这为底层手写优化和非标准算子（如非规则访存、动态形状）提供了充足的实现空间。
-   XLA 编译器生态（面向 TPU/GPU）：XLA 以全局图级视图运作，核心优势在于执行激进的算子融合（Operator Fusion），将多个操作融合成单一底层指令块，将中间激活值锁定在片上内存中。然而，XLA 是基于规则的静态编译模型，当遇到无法有效映射到二维脉动阵列的非规则操作时，其自动化调度可能面临效率降级。
-   Pallas 与 Keras 前端：为屏蔽底层差异，Google 提供了分层工具。Keras 3 作为统一前端，支持同代码跨后端运行；而当 XLA 的自动优化无法满足特定非规则算子需求时，Pallas 允许开发者绕过高层 API，直接编写针对 TPU VMEM 和硬件特性的内核代码，实现精确的物理干预与瓶颈隔离。

## 3. 实验探针：蝶式矩阵与非规则访存挑战

为量化观察上述架构差异，本研究引入蝶式矩阵（Butterfly Matrix）作为测试探针。

标准全连接层（Dense）为 $O(N^2)$ 的稠密矩阵乘法，完全契合 MXU 和 Tensor Core 的加速路径。而蝶式算法通过分治法将矩阵分解为 $\log_2 N$ 层稀疏因子，将复杂度降至 $O(N \log N)$。在 $N=1024$ 规模下，其参数量仅为 Dense 的 ~1/22。

然而，蝶式算法的物理执行过程包含严格的跨步距非连续数据重排（Gather/Scatter）。这种离散的内存寻址与 TPU 脉动阵列所需的连续空间数据流存在结构性冲突，理论上会触发 GPU（依赖通用 SIMT 容忍不规则访存）与 TPU（依赖规则数据流）的不同行为响应。

## 4. 实验数据与架构印证

我们分别在 NVIDIA P100 GPU 与 Google TPU v5e 上执行了严格对照的基准测试，数据直接印证了前述的微架构论述。

### 4.1 跨硬件算法一致性验证 (Keras 抽象层)
在 Fashion-MNIST 任务中，利用 Keras 训练相同结构的纯 MLP 网络。
-   参数与精度：Dense 基线参数约 210 万，验证集精度 88.20%；蝶式 B2 模型参数约 9.2 万，在 TPU 和 GPU 上分别测得 87.08% 与 85.83%。
-   结论：参数压缩未导致表征能力严重损失。同一套高层代码在跨平台硬件上得出一致的收敛结果，验证了框架分层抽象的可靠性。

### 4.2 算子级吞吐与微架构敏感度 (JAX 编译层)
固定规模（$N=8192, \text{Batch}=1024$），测量单次前向执行延迟：

| 算子类型                | TPU v5e 延迟 | GPU P100 延迟 | TPU 绝对加速比 |
| :---------------------- | :----------- | :------------ | :------------- |
| 原生 Dense matmul       | 0.746 ms     | 15.970 ms     | 21.4x-      |
| 蝶式 B2 算子            | 2.122 ms     | 20.000 ms     | 9.4x-       |
| 相比 Dense 相对惩罚 | 2.84x-    | 1.25x-     | —              |

-   结论印证：对于规则的 Dense 运算，TPU 展现出 21.4 倍的绝对优势，直接体现了 MXU 脉动阵列硬连线设计的极致吞吐量。而对于包含非规则访存的蝶式算子，GPU 的 SIMT 架构通过动态调度较好地吸收了非规则访存开销（仅增加 25% 延迟）；TPU 则因数据流不规则无法完全利用 MXU，延迟惩罚达到 2.84 倍。

### 4.3 物理瓶颈的精确归因 (Pallas 控制层)
为查明 TPU 上 2.84 倍惩罚的根源（是 HBM 带宽阻塞还是计算单元降级），我们在 $N=1024$ 尺度下，利用 Pallas 强制将全部计算驻留在 VMEM 内完成单 Kernel 融合。

| 实现方式 (TPU v5e, N=1024)   | 执行延迟  | 相对 Dense |
| :--------------------------- | :-------- | :--------- |
| Dense matmul (MXU 基准)      | 0.0407 ms | 1.00x      |
| 蝶式 (XLA 自动编译调度)      | 0.1187 ms | 2.91x      |
| 蝶式 (Pallas 手动 VMEM 驻留) | 0.1296 ms | 3.18x      |

-   结论印证：即便 Pallas 从物理层级消除了跨层级的 HBM 数据往返，蝶式算子耗时并未改善。这证明瓶颈不在于存储体系架构（内存墙），而在于计算体系架构——离散访存模式无法映射到 MXU，必须由通用向量单元执行，导致吞吐量结构性折损。同时，XLA 编译结果与 Pallas 手动优化耗时相近，说明对于片上内存充裕的任务，XLA 的静态调度机制已能自动完成最优的内存排布。

## 5. 总结

本文从物理机制出发，通过实验证实：GPU 的 SIMT 架构通过复杂的动态调度换取了对非规则计算逻辑的高宽容度；TPU 则通过牺牲分支灵活性与非连续访存效率，在脉动阵列上换取了针对连续稠密计算的极高吞吐表现。理解算法访存模式与底层微架构的匹配关系，并合理应用 Keras、JAX 与 Pallas 构建从高层构建到底层诊断的完整技术链路，是实现异构计算平台性能最大化的必要工程实践。
